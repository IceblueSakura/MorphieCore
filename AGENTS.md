# MorphieCore Agent Instructions

## Project and sources of truth

- MorphieCore hides Provider differences behind one typed IR. pi and opencode are the primary clients. Routing is cache-affine failover, not load balancing.
- [README](README.md#documentation-map) is the document entry point. [Architecture](docs/architecture/index.md) (with specialized domain modules in `docs/architecture/`) owns accepted principles and decisions; [Roadmap](docs/roadmap/index.md) (with lifecycle documents in `docs/roadmap/`) owns scope, execution dependencies, the unified unscheduled issue register and gates; [API expansion design](docs/api-expansion-design.md) owns unselected proposals; [Usage](docs/usage/index.md) owns operating procedures; [Development](docs/development.md) owns shared development conventions and overall acceptance status. Code and tests describe current behavior, not authority over official protocols; read catalogs and startup code for current Providers, models and bindings.

## Working approach

- Follow the [accepted standards-reset design](docs/architecture/decisions.md#scope-and-activation-decisions) and [remaining roadmap gates](docs/roadmap/index.md#planned-order) before further stage-4 implementation. Pin current stable dependencies and release sources first; integrate upstream-derived standard tests while rewriting, not after restoring old mappings. Deferred counting and unscheduled stage 5 remain; union design does not activate new APIs.
- Investigate proactively: trace actual client workflows, primary protocol sources and existing implementations. Challenge weak premises, compare alternatives and recommend simpler designs with concrete trade-offs.
- Own implementation choices within the agreed scope. Explore and propose architectural improvements; when a semantic or structural decision is unresolved, show a minimal counterexample and a recommendation for user selection. Continue independent work meanwhile. Research does not reopen frozen implementation scope.
- Develop small, coherent slices. State consequential behavior goals and exit conditions in the roadmap, but choose the investigation, prototyping and verification sequence that fits the uncertainty. Do not turn every change into a test-first ritual or a new framework.
- Follow the user-approved [partial-delivery exit](docs/roadmap/index.md#partial-delivery-exit): usable principal workflows, recorded low-loss conversions and verified affected paths. Keep uncertain cells in the [unscheduled issue register](docs/roadmap/unscheduled-issues.md#unscheduled-issues) rather than requiring every observation to close.

## Authorization

- Work on `main`; preserve unrelated changes. Commit and push completed slices to `origin/main` after the verification below. Deployment, other publication and credential lifecycle operations require explicit approval.
- Development-related real Provider calls are authorized without per-call confirmation or a spending cap. Fix the target, request count, output cap and timeout before each run; run serially without hidden retries, using the project loader and redacted reporting only.
- Approved phases allow large deletions and breaking rewrites without compatibility shims. Frozen implementation gets only necessary maintenance.

## Security

- Access credentials only through the project loader. Never inspect `.env`, private configuration, OAuth files or third-party auth caches as investigation/test input, or print environment values.
- Keep credentials, private config and business payloads out of source, public fixtures and tool output. The single deployer owns every downstream client and authorizes sensitive business headers/bodies in explicitly enabled, bounded [private failure context](docs/architecture/runtime-and-routing.md#configurable-exchange-capture). Authentication is always redacted before capture; ordinary telemetry stays body-free. Private capture is not permission to publish payloads or use them as protocol fixtures.
- Preserve loopback-only ingress, fail-closed auth and trusted target selection. Business data cannot choose origins, credentials or auth/proxy headers; credential locators and trusted origins never reach clients. Bound resources and time, release upstreams on cancellation, and never replay after publication or fabricate successful termination.

## Engineering

- `src/semantic` is the official-protocol semantic union, with one authoritative owner per fact and no protocol, Provider or execution dependency. Keep targets, credentials, retries and adaptation-publication state outside it; codecs/lowering are pure. Protocol spelling and raw wire belong in codecs, not vendor bags or duplicate semantic containers.
- Keep known fields strict and ignore unknown ones. Walk the [conversion ladder](docs/architecture/adaptation-and-dialects.md#conversion-ladder) in order: same-name carrier, same-semantic substitution, partial lossy substitution, then omission; reject only when a field is inexpressible and omitting it would let the client mistake the response for satisfying its request. Rejection needs that reason; admission does not need prior equivalence evidence, and unknown upstream behavior is delegated to upstream validation rather than pre-rejected. The ladder never weakens trust, bounds, malformed-known-value checks, identities or terminal honesty. Explicit guarantees retain rejection unless the user selects a concrete named relaxation, such as [Bailian function strictness](docs/architecture/adaptation-and-dialects.md#shared-aliyun-billing-dialect). Public APIs default to official baselines; only explicitly selected semantic profiles may extend them, independently of Provider dialects.
- Follow the [Client semantic boundary](docs/architecture/adaptation-and-dialects.md#field-handling) and discard unknown extension fields without IR retention or Provider passthrough. Same-semantic and lossy ladder rules need a named rule and a disposition-table entry, not per-rule confirmation; lowering a content field or explicit guarantee below rejection still needs user selection. Diagnostic output is optional, needs protocol-permitted extension positions and never requires client echo.
- Prefer existing solutions and direct code over speculative abstractions. Add checks for concrete failures and remove obsolete code. Update `Cargo.lock` for dependency changes and verify with `--locked`.
- Maintain only the current application configuration schema and paths. The operator owns using current configuration; do not add historical aliases, migrations, obsolete-field detection or dedicated old-schema rejection tests. Keep ordinary strict parsing and current credential, target and resource safety checks; current Provider wire contracts are a separate concern.
- Name code, fixtures and tests by protocol or behavior, not roadmap phases or package IDs. Keep scheduling identifiers in planning and acceptance documentation.
- Write all documentation, comments and commits in concise English. Do not inspect/edit build caches by hand or commit `testdata/{generated,reports,dist,runtime}/`.

## Tests

- Adapt production client boundaries and actual Agent acceptance only to the host's current latest pi, OpenCode and other Agents. Remove obsolete client-specific compatibility instead of retaining old-version pins, branches or a historical-version matrix; never downgrade to match source pins. Recharacterize relevant behavior after updates without maintaining tested-version inventories in documentation. Protocol/SDK/source pins remain independent reference and regression baselines. Use isolated test-owned state and safe unwrapped launchers without changing host credentials or personal configuration.
- Keep tests that independently challenge a product assumption, public contract or concrete external failure risk. Aggressively delete implementation restatements, static catalog/configuration snapshots, trivial accessor/assembly checks, third-party self-tests and redundant permutations. Do not add replacement tests merely to preserve removed assertions or test counts. Follow the roadmap's phase-specific scope.
- The [standards-reset design is human-approved](docs/architecture/decisions.md#scope-and-activation-decisions). Implement its integrated upstream-source test plan with each slice; unresolved concrete semantics and new integration still need their own selection. Historical mapping expectations are not the regression oracle, even if previously approved.
- Follow the [diagnostic-extension scheduling exception](docs/roadmap/index.md#observability-follow-up): safe-to-ignore fields may be added now without dedicated extension tests; information organization/aggregation and those tests await the deployer's final production-preparation decision. Existing standard Agent-loop, authoritative evidence and safety checks remain required.
- Protocol mappings need independent wire→IR and IR→wire expectations from current official contracts and pinned upstream assets; a round trip alone is not evidence. Prefer thin fixture adapters and real SDK consumers over repeatedly rewritten local snapshots. Local IR checks need a concrete product invariant; negative cases must reach their intended failure.
- Preserve credential/auth, lifecycle/cancellation, bounds, origin, strict-JSON, replay-isolation and terminal-honesty assertions. Delete obsolete tests and their exclusive helpers/dependencies together; follow [test selection and pruning](docs/development.md#test-selection-and-pruning). Coverage and test counts are not execution, progress or acceptance criteria.

## Verification

- Use focused offline checks while iterating; reuse valid evidence instead of rerunning the suite after every edit. Before publishing an implementation slice, run the [full offline baseline](docs/development.md#offline-baseline) and applicable roadmap gates. Documentation-only changes need [documentation checks](docs/development.md#documentation-checks), not Rust/SDK runs.
- Keep SDK, real-client and Provider acceptance separate from offline regression. Report actual checks, failures and unverified contracts; compilation, coverage percentages and synthetic success do not prove full-chain behavior.

## Documentation

Keep the document set: `README.md`, `AGENTS.md`, the architecture domain modules in `docs/architecture/`, the lifecycle roadmap in `docs/roadmap/`, the operational guides in `docs/usage/`, `docs/{development,references}.md`, the [API expansion design](docs/api-expansion-design.md), the separately requested [Provider account plan](docs/provider-account-redesign-plan.md) and [Convergence cleanup plan](docs/convergence-cleanup-plan.md), `docs/openapi.json`, and sourced, dated protocol notes in `docs/refs/`. Development summarizes overall acceptance status. Acceptance notes are temporary development material, not a permanent archive: omit historical run classifications, execution dates, tested-version inventories, acceptance commands and per-run evidence catalogs. Unresolved issues and repair/defer dispositions have one home in the roadmap, and accepted adaptations belong in the architecture. Do not retain phase-specific review pages or add run reports/history pages. The Provider account plan owns the detailed accepted account/recovery contract; the cleanup plan retains remaining cleanup boundaries and external gates, not completed task history or a second issue register. Deployment and credential operations retain separate authorization. Remove finished roadmap slices and record meaningful decisions in the architecture decision table.

Organize each document by domain with shared rules above specialized branches. Keep one authoritative home per topic and link to it instead of maintaining duplicate plans or specifications. Separate proposed design, accepted decisions, implementation status and acceptance evidence; a structural edit grants no approval. Preserve source dates in research notes and use [References](docs/references.md#research-notes) as their index.
