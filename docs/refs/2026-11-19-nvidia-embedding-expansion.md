# NVIDIA Embedding expansion research

Sources and account-scoped observations checked on 2026-11-19. **Research only.** No NVIDIA Embedding route, API extension, dependency, deployment or implementation order is approved by this note. [Architecture](../architecture/index.md#independent-embedding-path) owns the accepted path; [the Embedding proposal](../proposals/tasks-and-counting.md#embeddings) owns unselected extension boundaries; [Stage 4](../roadmap/index.md#stage-4-scope) owns scheduling and gates.

## Hosted contract and evidence

Primary sources: NVIDIA Build [1B request/response schema](https://docs.api.nvidia.com/nim/reference/nvidia-nemotron-3_5-embed-1b-infer.md), [8B request/response schema](https://docs.api.nvidia.com/nim/reference/nvidia-nemotron-3_5-embed-8b-infer.md), and NeMo Retriever NIM 2.4 [usage](https://docs.nvidia.com/nim/nemo-retriever/embedding/latest/use-the-api-openai.html) and [model support](https://docs.nvidia.com/nim/nemo-retriever/embedding/latest/support-matrix.html). The `latest` pages described 2.4 at review time; hosted Build is a different service, not a claim about that NIM release.

| Hosted NVIDIA Build ID | Default dense width | Documented `dimensions` range | Observed default-width text calls |
|---|---:|---:|---|
| `nvidia/nemotron-3.5-embed-1b` | 2048 | 128–2048 | `query` and a deliberate `passage` recheck returned 200/2048; omitted `input_type` returned 400 |
| `nvidia/nemotron-3.5-embed-8b` | 4096 | 1–4096 | `query` and `passage` each returned 200/4096 |

The configured account's `/v1/models` listed both IDs. The probes used the project loader and single synthetic text samples with `truncate:"NONE"`. Across nine inference calls there were no automatic retries and one deliberate recheck. The initial 1B passage call had no verified HTTP outcome; its deliberate recheck succeeded and reported the exact model ID and both usage counters.

On 8B `query`, explicit `dimensions:256` returned both a 256-element finite JSON float array and, in a separate Base64 request, 1,024 decoded bytes consistent with 256 finite little-endian binary32 values. Both responses reported the expected model ID and prompt/total counters. This establishes the observed shapes, not bit-for-bit equivalence between calls. An over-length repeated synthetic input with `truncate:"NONE"` returned HTTP 400 and no vector; the probe did not distinguish a byte cap from a tokenizer boundary. These are direct upstream checks, not gateway or SDK qualification, and do not validate every width, batching, image input, or quantized representation.

Both hosted models use `POST /v1/embeddings` with bearer authentication. They share the following documented surface; it is not all qualified by the probes:

- **Purpose:** prose requires `input_type:"query"|"passage"`, though the OpenAPI `required` arrays list only `input` and `model`. Text can serve either purpose; images are passage-only. Identical text can legitimately be used once in each role. A scalar string, a one-element array, or text that looks like a question cannot distinguish them.
- **Sample shape:** `input` is a string or a list of strings. A hosted sample can be text, one inline PNG/JPEG, or text followed by one inline image, rendered in a string as a data URL or an image tag. `modality` may be inferred or given for the whole request or per sample. The wire spelling does not turn that string into generic downstream media admission. A remote image fetched in an example is not an API guarantee of URL fetch.
- **Overflow:** the hosted schema advertises a 10,240-token limit, `truncate:"END"` by default, and `"NONE"` for rejection. `"START"` is unsupported. The passage prefix and image block must fit independently of text truncation. This is not the checkpoint's 32,768-token limit; the self-hosted deployment's configured and byte limits also differ. Use the hosted refusal path rather than estimated token counts if no exact tokenizer contract is qualified.
- **Result:** dimension reduction is documented as re-normalizing the shortened vector. `embedding_type` selects numeric values or packed values; `encoding_format` selects a wire representation and defaults to `float`. The hosted schema lists `float`, `int8`, `uint8`, `binary` and `ubinary` as value types, but the schema alone does not qualify those combinations. NIM 2.4 explicitly excludes `binary`/`ubinary` for self-hosted 1B and its table lists a different 8B width than hosted Build. Do not reconcile the two by inheriting a default. A checkpoint's BF16 or NVFP4 precision is not an output vector type.

NIM documents `-query`/`-passage` model suffixes as an OpenAI-compatible carrier for its NV-Embed-QA example. This is a useful precedent for **public MorphieCore labels**, not evidence that NVIDIA Build accepts suffixed IDs for either new target. Egress would send the exact hosted ID and its explicit `input_type`.

## Cross-provider discriminators

These source comparisons isolate design decisions rather than propose a broader integration queue. No inference was run against the comparison services.

| Source | Discriminator for the Stage 4 design |
|---|---|
| [OpenAI Embeddings](https://developers.openai.com/api/reference/resources/embeddings/methods/create) | Standard clients can select `model`, `dimensions` and `encoding_format`, but not retrieval purpose, input modality, quantization or truncation. `base64` is not a dtype declaration. Preserve its existing text/token and result contract. |
| [Gemini Embedding guide](https://ai.google.dev/gemini-api/docs/embeddings) and [current Google contract](2026-10-22-embedding-image-contracts.md#google-embedding-selection) | Native multi-Part input can aggregate into one vector. Embedding 2 has no `task_type` field (unlike 001); caller-authored text can express a task, but gateway prefix injection is not equivalent to a native control. |
| [Cohere Embed](https://docs.cohere.com/reference/embed) | One request-wide purpose can express `search_query`, `search_document`, `classification` or `clustering` independently of joint input content. Multiple `embedding_types` can return more than one representation of the same sample. A list of vectors with no type association cannot express it. |
| [Voyage multimodal Embeddings](https://docs.voyageai.com/reference/multimodal-embeddings-api) | Omitted purpose means no retrieval prompt; `query`/`document` are optional and a query can contain an image. Its default truncation can remove an entire image; explicit `false` requests an error. Neither the default nor the NVIDIA text-only-query rule belongs in shared IR. |
| [Titan Multimodal on Bedrock](https://docs.aws.amazon.com/bedrock/latest/userguide/model-parameters-titan-embed-mm.html) | Combining text and image averages separate vectors. Admitting the same two modalities does not prove equivalent joint encoding or a shared embedding space. |
| [OpenRouter Embeddings](https://openrouter.ai/docs/api/api-reference/embeddings/submit-an-embedding-request) | Contextual documents are ordered lists of chunks, yielding a vector per chunk with document association. This is neither a batch of independent samples nor joint inputs producing one vector per sample. Preserve a separate relation if this feature is later selected. |
| [LanceDB's NVIDIA integration](https://docs.lancedb.com/enterprise/v1-12-0/integrations/embedding/nvidia) | A real consumer chooses `passage` for ingestion and `query` for search with one configured embedding model. Its text-only/float selection is a credible first slice; its default end truncation and retry count are client policy, not gateway policy. A client with one opaque model setting for both methods would need a wrapper or an explicit purpose API to use two model labels. |

## Implications for MorphieCore

The following are design findings, **not implemented changes**.

- **Preserve a standard ingress.** [`openai/embeddings.rs`](../../crates/morphiecore-protocol/src/openai/embeddings.rs) and the public OpenAPI schema currently have no purpose carrier. Putting an opaque provider field into a text request would neither preserve the baseline nor support the one-model/two-roles workflow consistently. If a later typed public contract is selected, purpose and overflow belong to the sample as proposed. A request-wide upstream field is sufficient only for homogeneous batches; reject mismatches rather than silently split or replace a role. Modalities are ordered sample content, not purpose flags. Keep independent, joint and contextual inputs distinct.
- **Plan an exact single target and space.** [`catalog.rs`](../../crates/morphiecore-catalog/src/topology/catalog.rs) currently emits one Embedding operation entry per binding, but [`topology/embeddings.rs`](../../crates/morphiecore-catalog/src/topology/embeddings.rs) rejects repeat provider entries. Multiple labels on NVIDIA would require one operation per trusted provider/path, rejection of conflicting paths, and separate public routes. Keep the origin, authorized path and credential loader outside business data. A query/passage pair is complementary only for its qualified service/model and processing contract. Equal widths or related names never justify failover, cross-model comparison, or index reuse after migration.
- **Check provider reports independently of delivery labels.** [`projection.rs`](../../crates/morphiecore-protocol/src/embedding/projection.rs) checks sample count and per-index width but does not correlate a reported model with the bound target. A same-width response from another model must not pass a qualified space check. Define exact or independently verified compatible reports, reject contradictions, and decide how to report absence and public role labeling without promoting bound provenance to an upstream report. Preserve reported usage separately; an estimate is neither a bill nor an admission token count.
- **Keep format and numerical type independent.** Reuse the existing float JSON / little-endian binary32 Base64 delivery rules for the first slice. Packed integers and bits require separately typed values, logical width, signedness, packing/padding rules and one representation association per sample, not conversion to floats or inference from a Base64 string. Reduced width is a model operation; do not synthesize it by slicing or normalizing the result locally.
- **Apply effective budgets, not just catalog maximums.** The existing [envelope](../../crates/morphiecore-protocol/src/embedding/envelope.rs) caps 128 inputs, 256 KiB input text, and 60,000 scalar values. At the observed native widths, the scalar bound alone limits 1B to 29 samples and 8B to 14; neither is evidence of a hosted batch limit. Enforce request/response bytes, deadline and cancellation independently. Scope image processing and response budgets separately if an image slice is selected; do not let the service infer image modality from ordinary client text.

## Recommended next selection

1. **Qualify 8B text retrieval first.** Both purposes succeeded at the native width, and 8B also has reduced-width encoding and over-length evidence. Scope a single unchanged text sample, explicit `truncate:"NONE"`, exact dense float source and standard float/Base64 client delivery. Start at the native width for both modes; broaden dimensions or batching only after checking both roles, bounds and per-index association. 1B is a separate space whose text roles also responded; qualify it separately and never switch models after a failure.
2. **Select the public purpose carrier before implementation.** Suffix-qualified public model labels keep `/v1/embeddings` compatible with ordinary SDKs; the application explicitly chooses one label per role, with no unqualified label or guessed default. This is the least invasive candidate. If consumers need one stable model identifier or must express purposes beyond the pair, choose a typed public task-purpose field/profile instead. A single fixed mode at the original label is only suitable if the selected workflow explicitly needs one role; it is not complete retrieval support.
3. **Qualify multimodal samples and quantized results independently.** For image passage input, distinguish standalone images and text-followed-by-image, preserve ordered typed parts, reject remote ingestion and wrong-purpose images, and test the actual size/sequence boundary. For quantization, pin wire representation and packing, use known-answer vectors and reject unsupported combinations. Do not couple either slice to contextual chunks, async Batch, rerank, storage, an index migration, or another provider.

For a later implementation, use independent request-wire and response oracles, not a reflection of the produced request. A test-owned authority should see exact IDs and purpose-selected wires; bad labels/dimensions, wrong purpose or over-budget input must produce no upstream send where local admission can decide. Return a valid wrong-model, same-width response to prove rejection before any result escapes, and separate valid float/Base64 cases to prove order, width, bytes and usage. Reuse [Embedding semantic tests](../../tests/semantic/embedding.rs), [gateway tests](../../tests/gateway/embeddings.rs) and [SDK loops](../../tests/sdk/embeddings.rs). Real completion, over-limit rejection, actual input order, report provenance and a small query/passage retrieval fixture qualify a selected binding; a successful sample cannot guarantee ranking quality or all supported parameter combinations.
