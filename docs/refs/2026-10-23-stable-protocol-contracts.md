## Anthropic API 2026-10-21

Sources: [migration guide](https://platform.claude.com/docs/en/api/migration-2026-10-21), [Python 2.0.0 release](https://github.com/anthropics/anthropic-sdk-python/releases/tag/v2.0.0), [selected 2.1.0 source](https://github.com/anthropics/anthropic-sdk-python/tree/9313f13a5a643ceed10fafba6785eab8e04b6e6e).

- `temperature`, `top_p` and `top_k` are removed from Messages/Batch requests; sending even a former default value returns 400. The guide states that no replacement restores a nondefault sampling effect. This is API-version semantics, not merely a model-specific SDK restriction.
- Documents directly in assistant messages reject; documents nested in returned tool results remain accepted. Nonempty text citations in user messages reject; assistant citations and document citation enablement remain separate.
- SDK API keys now use `Authorization: Bearer`; the service still accepts either Bearer or `X-Api-Key`. A client holds one credential. Preserve ingress rejection of ambiguous credentials rather than accepting both indiscriminately.
- `MessageParam` becomes role-discriminated. Dict input remains valid; generic construction/subclassing assumptions require review.

**HTTP recheck, 2026-10-24:** the pinned SDK's [_constants.py](https://github.com/anthropics/anthropic-sdk-python/blob/9313f13a5a643ceed10fafba6785eab8e04b6e6e/src/anthropic/_constants.py) sets `ANTHROPIC_API_VERSION = "2026-10-21"`; [_client.py](https://github.com/anthropics/anthropic-sdk-python/blob/9313f13a5a643ceed10fafba6785eab8e04b6e6e/src/anthropic/_client.py) sends it by default. Under the user's [latest-only decision](../architecture.md#protocols), Messages POST now requires one matching header before body collection. Native preparation and the manual probe use the same fixed version; they do not forward ingress version/beta headers or retry a downgrade. Removed sampling fields reject at public/native intake, including null/former defaults, and their Messages DTO/encoding paths are deleted. The existing selected fixed-sampling projection for other source protocols remains separate from native carrier support. Live Provider/version acceptance remains unverified.

**Ordinary-tool defaults recheck, 2026-10-24:** pinned Python [ToolParam](https://github.com/anthropics/anthropic-sdk-python/blob/9313f13a5a643ceed10fafba6785eab8e04b6e6e/src/anthropic/types/tool_param.py) and TypeScript [Messages tool types](https://github.com/anthropics/anthropic-sdk-typescript/blob/5badc765f17d373405f300ee8e69e7f490b1f172/src/resources/messages/messages.ts) permit nullable `cache_control` and `eager_input_streaming`. ## Google API versions and semantic differences

Sources: [API versions](https://ai.google.dev/gemini-api/docs/api-versions), [Interactions v1 schema](https://ai.google.dev/static/api/interactions-v1.openapi.json), [v1beta schema](https://ai.google.dev/static/api/interactions.openapi.json), [v1 Discovery](https://generativelanguage.googleapis.com/$discovery/rest?version=v1), [v1beta Discovery](https://generativelanguage.googleapis.com/$discovery/rest?version=v1beta), [thinking](https://ai.google.dev/gemini-api/docs/thinking), [Interactions overview](https://ai.google.dev/gemini-api/docs/interactions-overview).

- SDK types span versions. Interactions v1 omits sampling controls that v1beta retains as deprecated. Current generateContent documentation also describes model families that ignore sampling; serializability does not prove effective control.
- Interactions documents signatures on thought/built-in-tool steps, not ordinary function calls; current v1/v1beta `FunctionCallStep` schemas omit `signature`. Prior observed ordinary-call signatures remain upstream compatibility evidence, not public-standard authority. The documented stream can start with an empty signature and later supply its delta; this does not permit discarding a completed required signature.
- Function/output schema descriptions explicitly identify ignored constraints. `VALIDATED`/`ANY` and matching schema JSON do not establish equivalence to every OpenAI strict constraint; tool choice and schema adherence are separate requirements.
- generateContent introduces `responseFormat.text.{mimeType,schema}` while retaining deprecated carriers. Source normalization must check conflicts and preserve one semantic owner.
- generateContent `store` controls request logging. Interactions `store` controls retained interaction resources/continuation. Neither is the gateway's private diagnostic-capture switch; do not merge these different meanings.
- Google Python 2.33.0 adds audio/document/video function-result subcontent, while the inspected public Interactions schemas enumerate text/image result arrays. Record this source disagreement; SDK breadth alone does not activate a public carrier.

The [Gemini 3 guide](https://ai.google.dev/gemini-api/docs/gemini-3) still documents `thinking_budget` backward compatibility, while the [3.8 migration guide](https://ai.google.dev/gemini-api/docs/whats-new-gemini-3.8) recommends `thinking_level`. Both selected Discovery versions declare `ThinkingConfig.thinkingBudget` as `int32`. These distinguish native wire support from preferred controls and model admission; they do not independently establish a live model budget guarantee. The gateway's exact-first budget check must agree with its explicit target admission, not infer support merely because an integer serializes.

Google web schemas are mutable; their version, revision and content fingerprints are recorded separately in the source lock. A changed digest requires review, not silent expected-output regeneration.

## Instruction authority research: current, legacy and Provider dialects

**Researched 2026-10-25, after the implementation review above.** This is a source-backed correction and design recommendation, not a change to accepted IR or conversion policy. Keep four facts separate: wire role spelling, the instruction author's authority, temporal placement/scope, and actual target model/dialect support. A successful parse, an SDK role union, or an OpenAI-compatible label proves neither effective hierarchy nor interchangeable roles. No Provider inference, private configuration or credentials were used.

**Subsequent selection and migration on the same date:** the user chose current-standard normalization in IR itself, explicitly including OpenAI system→developer, then authorized implementation. The [canonical instruction contract](../architecture.md#instruction-authority-and-canonical-roles) owns mappings and lifetime; [Development](../development.md#verification-gates) records directional, SDK and installed-client evidence. Root blocks no longer become ordered history, and Provider deviations stay in dialects. The research below retains its source distinctions: selecting a canonical mixed-role interpretation does not turn undocumented historical or Provider behavior into a proven universal alias.

### OpenAI: API system is not automatically Model Spec system authority

The current pinned [Chat system type](https://github.com/openai/openai-python/blob/e8a0fd28bbdc1699c97ff0f602b1af3dd378382d/src/openai/types/chat/chat_completion_system_message_param.py) calls its content **“Developer-provided instructions”** and says to use developer messages with o1 and newer. The [developer type](https://github.com/openai/openai-python/blob/e8a0fd28bbdc1699c97ff0f602b1af3dd378382d/src/openai/types/chat/chat_completion_developer_message_param.py) uses the same author description and says developer messages **“replace the previous `system` messages.”** The [reasoning guide](https://developers.openai.com/api/docs/guides/reasoning-best-practices) supplies a sharper migration boundary: **“Starting with `o1-2024-12-17`”**, reasoning models support developer rather than system messages.

By contrast, the dated [Model Spec, 2026-08-18](https://model-spec.openai.com/2026-08-18.html) says **“System-level instructions can only be supplied by OpenAI”** and places that authority above developer. Do not equate that vendor-reserved authority with every caller-supplied JSON field named system. The [o1 System Card](https://openai.com/index/openai-o1-system-card/) describes system-over-developer training/evaluation and the introduction of custom developer messages; it does not grant API callers vendor authority through legacy spelling.

Consequently, legacy API system → current developer is a documented application-instruction migration, not automatically a demotion. The reverse can be an application-authority-preserving compatibility mapping when the target's operator slot is system; it is not automatically privilege escalation. Neither statement establishes a universal alias, identical model behavior, or the collision rule when both API roles occur in one request. Current [Responses input types](https://github.com/openai/openai-python/blob/e8a0fd28bbdc1699c97ff0f602b1af3dd378382d/src/openai/types/responses/easy_input_message_param.py) say developer **or** system outranks user, without specifying priority between those two caller-provided roles.

| Historical boundary | Original evidence | Interpretation |
|---|---|---|
| Earlier Chat schema | Python v1.54.0, [immutable message union](https://github.com/openai/openai-python/blob/b32507dd793b6b1dc218f76f7b485ae441db8841/src/openai/types/chat/chat_completion_message_param.py), 2024-11-04: system but no developer | Historical application-instruction spelling; SDK schema is not every model's support matrix |
| o1-preview/o1-mini launch | [2024-09-12 announcement](https://openai.com/index/introducing-openai-o1-preview/) explicitly excludes system-message support | Do not apply the later o1 migration rule to every model whose name begins with o1; user text cannot recreate a missing authority channel |
| Production o1 | Python v1.58.0, [immutable union](https://github.com/openai/openai-python/blob/1b78f22ddf4b64542b39804882fca388a62355fb/src/openai/types/chat/chat_completion_message_param.py), 2024-12-17: developer and system; reasoning guide names the model revision | Select by actual target contract, not a global version/name heuristic |
| Current Chat | Verified source pin v3.37.0 plus current official guide | Both wire roles exist; developer replaces legacy application system for applicable models |

Responses [create types](https://github.com/openai/openai-python/blob/e8a0fd28bbdc1699c97ff0f602b1af3dd378382d/src/openai/types/responses/response_create_params.py) define root instructions as **“A system (or developer) message inserted into the model's context.”** The [text guide](https://developers.openai.com/api/docs/guides/text) calls an explicit developer input message **roughly equivalent**, and explicitly limits root instructions to the current generation request: predecessor instructions are not carried over with `previous_response_id`. Root instructions therefore do not imply a distinct vendor-reserved tier or a universal exact developer-message alias.

The older [Responses v1.66.3 create type](https://github.com/openai/openai-python/blob/9dea82fb8cdd06683f9e8033b54cff219789af7f/src/openai/types/responses/response_create_params.py), 2025-03-12, said “as the first item”; the current type says “inserted” without that precise position. Keep the gateway's leading-carrier rule as its selected representation, not a claim that the newest generic OpenAI description promises an exact insertion index. The guide's priority-over-input example uses a user prompt; it does not settle conflicts with additional developer/system input items.

### Messages: operator system, placement and version are independent

Current [Messages create](https://platform.claude.com/docs/en/api/http/messages/create) accepts root system as a string or text-block array. The pinned [SystemMessageParam](https://github.com/anthropics/anthropic-sdk-python/blob/9313f13a5a643ceed10fafba6785eab8e04b6e6e/src/anthropic/types/system_message_param.py) and role union also admit explicit mid-conversation system; there is no native developer role.

The [mid-conversation guide](https://platform.claude.com/docs/en/build-with-claude/mid-conversation-system-messages) identifies system as coming from **“you, the application operator”**, and says system instructions win conflicts with user instructions. [Messages usage](https://platform.claude.com/docs/en/build-with-claude/working-with-messages#system-role-in-messages) gives mid-conversation and root system **the same authority**. Later conflicting system messages prevail prospectively, including over root system for subsequent turns. This is conflict precedence, not wholesale deletion of all earlier instructions.

Anthropic's [constitution](https://www.anthropic.com/constitution) separately discusses Anthropic, operators and users, with operators typically acting through system prompts. That training-intent document is not proof of hidden wire messages or perfect behavioral adherence. Published claude.ai/mobile [system prompts](https://platform.claude.com/docs/en/release-notes/system-prompts/overview) explicitly do not apply to the API. Mapping caller-controlled Messages system to OpenAI application developer is therefore conceptually sound; treating it as OpenAI-reserved system authority is not.

### Directional conversion recommendation

| Source → target | Evidence-backed relation | Conditions / remaining selection |
|---|---|---|
| Legacy OpenAI application system → current OpenAI developer | Documented migration of the application instruction channel | Use actual target support; do not infer from the role name alone or apply to preview models without that channel |
| Current OpenAI developer → legacy/provider operator system | Recommended compatibility carrier for the same application-author role, not inherently an elevation | Target must actually honor system; preserve content/order/scope and declare non-exact changes. Backend alias and identical model behavior are not proven |
| Messages root system → current OpenAI developer or Responses instructions | Appropriate application-authority mapping | String/block form must not choose authority or lifetime. Preserve root scope and any per-part cache semantics; the two target carriers have different continuation behavior |
| OpenAI developer → Messages system | Appropriate operator-channel mapping, with target-specific representation constraints | Leading instructions can use root; later instructions need supported native placement. Do not hoist across user/assistant turns or erase temporary scope |
| Responses instructions → Chat instruction message | Official guide supports rough equivalence, not a new authority tier | Select developer/system by target; independently retain current-request lifetime instead of inheriting old root instructions |
| Any privileged application instruction → user text | Authority loss, not equivalent migration | No heading, prefix or wording restores missing priority. Do not silently use this fallback |
| Mixed caller system + developer → one role | No universal exact conflict rule established | Preserve source order and original role evidence; do not invent a universal system>developer ranking. Choose target-conditioned same-channel normalization only after reviewing collisions |

**Recommendation for MorphieCore:** revisit the premise that the two IR enum spellings necessarily represent universally different authority levels. Model application/operator authority separately from root versus ordered placement, continuation lifetime and source-role evidence; choose wire spelling in the target adapter. Messages root string and block forms should normalize to the same semantic instruction channel and scope, without discarding cache ownership. This is a design direction, not approval of a new enum/schema or a lossless mixed-role collapse. Preserve exact native carriers first while the unresolved target-specific rules remain explicit.

The first review's “developer→system may raise privilege” warning was too broad. A privilege change must be assessed from **source and target author semantics**, not raw role names. The demonstrated Messages string/block difference still needs repair, but its proven defect is representation-dependent semantic ownership/lifetime; priority degradation on modern OpenAI is not established merely by observing developer versus system.

Remaining uncertainty: mixed-role conflict treatment, undocumented DeepSeek/Alibaba Chat developer support, Token Plan-specific normalization and per-route OpenRouter behavior. Source/SDK contracts establish intended representation, not guaranteed model compliance or measured capability. No implementation, source-pin promotion, additional model admission or new API activation follows from this research.

### Minimal counterexamples and disposition

Synthetic calls through the real `prepare_with_rules` path confirm that NVIDIA Chat and Zhipu Chat currently prepare `developer(R), user(U)`, `developer(R), developer(P), user(U)`, `user(U), developer(P), user(V)`, and multipart instruction arrays without rejection. Zhipu Responses prepares explicit developer instructions without `type:message`. These are local prepared-body observations, not upstream HTTP calls. The temporary probe covers nine existing binding/operation pairs and four instruction shapes, including Token Plan Chat. Its first Go run failed because the pure caller omitted required conversation context; after supplying explicit synthetic context, preparation succeeds and confirms current developer output. That prerequisite failure is not a role verdict.

There is also a documented multipart-shape gap in the already selected Bailian Chat mapping: string system content is required by the Provider reference, while the generic Chat encoder emits arrays for multipart instruction owners. Do not confuse a correct role choice with complete instruction representability.

Recommended bounded correction:

1. Zhipu Chat: use its system application carrier; validate string representation. Zhipu Responses: preserve developer and materialize the required message discriminator, without changing root/history lifetime.
2. NVIDIA: resolve the exact hosted contract and validate model/operation-specific shape and placement. Start with the evidenced single initial string instruction; do not move later instructions or merge root/history owners silently. Leave hosted Responses separately unverified.
3. Review a named, bounded text-part composition versus rejection for string-only Chat targets, including Bailian. No new composition rule is selected by this audit.
4. For Go, ModelBest, Grok and OpenRouter, close the specific hosted/model/route evidence gaps before asserting native fidelity. Do not infer developer rejection merely because another SDK emits system, or apply a blanket system mapping across operations.

Do not copy Vercel's generic [Open Responses converter](https://github.com/vercel/ai/blob/594495a5af70547d9d7a13d6df334ae30db49622/packages/open-responses/src/responses/convert-to-open-responses-input.ts#L490-L495): it collects every system message and joins them into root instructions, including instructions encountered after user content. That loses ordered placement under MorphieCore's selected contract. Keep canonical Developer IR; put validated carrier changes in target dialects. This review neither selects those repairs nor certifies every parameter, live Provider behavior or a new Vercel package execution baseline.

**Selected follow-up, 2026-10-25:** the user subsequently authorized the recommended repairs without additional tests. The [implemented contract](../architecture.md#instruction-authority-and-canonical-roles) selects conservative rejection rather than introducing text composition. Reusing the same preparation probe confirms Zhipu's Chat system/Responses typed-developer split, rejection of string-target multipart instructions, and the exact NVIDIA Chat binding's single-initial-instruction boundary.
