## Exact carriers and source validation

### Google foreground contracts, 2026-10-20

The [Interactions v1 reference](https://ai.google.dev/api/interactions-api-v1) and pinned Google SDK [`78f6d34`](https://github.com/googleapis/python-genai/tree/78f6d3412caaaed44f99ce57be2d16d0b8c407cb/google/genai/_gaos/types/interactions) distinguish nested created/completed resources from top-level status updates. The nested resource descriptions and SDK require `id`/`status`, although the rendered reference labels those fields optional; updates require `interaction_id`/`status`. Both native lifecycle resources and status updates declare decode continuation tokens in the SDK. `event_id` is a separate resumption marker, not permission to resume.

The public six-status union includes `in_progress`, `requires_action`, `completed`, `failed`, `cancelled`, `incomplete`. SDK updates additionally include `queued` and `budget_exceeded`; that does not widen the selected v1 foreground profile. Neither source establishes a transition graph or final equality with an earlier terminal-like update. A schema-expressible `requires_action → in_progress → final completed` sequence is a policy counterexample, not observed Provider behavior. The [streaming guide](https://ai.google.dev/gemini-api/docs/interactions/streaming) explicitly ends a tool-call stream with `interaction.completed` carrying `requires_action`; its REST examples use v1beta, not the selected v1 path.

The [generateContent function-calling guide](https://ai.google.dev/gemini-api/docs/generate-content/function-calling#multimodal-function-responses) documents singleton `{"$ref":"displayName"}` objects, unique inline-part names and at most one reference per name. An ordered `response.output`/`error` array can therefore keep text and media occurrences distinct without concatenation. The exact array is the gateway's projection convention, not an official prescribed output schema. See [multimodal source discrepancies](multimodal.md#tool-result-media); this is not Provider acceptance.

The [pinned Google proto](https://github.com/googleapis/googleapis/blob/8cc2927c2ea64e6876568683050deabf2b52ce56/google/ai/generativelanguage/v1beta/generative_service.proto) declares token `log_probability` and signed-int32 `token_id` optional. Omission is not a reported zero. `finish_message` explains an existing finish reason; average/sum log probabilities are independent reported aggregates. A candidate containing text `"A"` plus `avgLogprobs:-0.25`, `logProbabilitySum:-0.25`, `finishMessage:"Generation ended normally"` or chosen `tokenId:42` loses a distinct fact if intake simply discards that field. URL retrieval errors/paywall/unsafe statuses are likewise not empty citation metadata.

Existing token probabilities can retain unknown bytes and sparse alternative facts. The 2026-10-21 exception selects a separate [terminal-explanation owner](../architecture.md#explanatory-terminal-reports); aggregates/token identity still need the [proposed owners](../api-expansion-design.md#google-output-report-owners-unselected), not a generic extras bag or reconstruction from token values. These checks used public sources and synthetic data; no real Provider behavior is established.

#### Interactions partial opening and service evidence, 2026-10-20

Later source review confirms that lifecycle resources are partial; SDK `model` is optional, while the current codec profile still requires it. The SDK has optional lifecycle `steps` and step-owned thought signatures. Function-call steps require ID/name/object arguments. Text/summary deltas carry no content-part index, so flattened streamed text cannot establish a later multipart array's original segmentation. Supplied-step reconciliation is therefore limited to proven single-part/empty content, with original source ordinals retained even when no semantic message was emitted. Step errors remain rejected rather than becoming response errors.

The [pinned SDK lifecycle type](https://github.com/googleapis/python-genai/blob/78f6d3412caaaed44f99ce57be2d16d0b8c407cb/google/genai/_gaos/types/interactions/interactionsseeventinteraction.py) includes `service_tier`; the inspected [beta reference](https://ai.google.dev/api/interactions-api) also lists it, while the inspected v1 page does not. Google's [Standard inference description](https://ai.google.dev/gemini-api/docs/optimization) describes normal processing and baseline pricing, semantically closer to OpenAI reported `default`/`StandardProcessing` than Messages committed `standard`/`StandardCapacity`. This is not identical pricing/performance or a selected v1 mapping. Do not infer lifecycle downgrade transitions or a report from request intent.

Two separately bounded real Developer API v1 structural probes used the project CLI loader and only Gemini 3.8 Flash Interactions: one request each, 64 output tokens, 45 seconds, one attempt, no SDK retries. Temporary opt-in upstream-response capture was inspected only for structural facts, never printed or used as fixture/replay input, then deleted. The typed-presence check found a string nested model, absent nested ID/status, and absent top-level ID/interaction-ID/status. Both clients received 502; intake stopped at opening, so this does not establish later lifecycle fields, tier absence for the complete stream, or honest final completion.

This native observation contradicts treating the SDK's mandatory fields as an unconditional v1 opening guarantee. The initial coarse check was insufficient to distinguish absence from invalid values; only the separate typed-presence probe establishes absence. The user subsequently selected [partial opening admission](../architecture.md#google-foreground-intake): absent creation ID/status are unreported, while supplied fields remain strict, including rejection of null. Bind the first real identity without synthesizing it; native creation is not a reported `in_progress` state. Model fallback and service-report admission remain independent selections.

A fresh CLI build with that selection passed the same bounded one-request structural recheck beyond creation: the following `interaction.status_update` reported string `in_progress` but omitted `interaction_id`, top-level ID and nested identity. Intake returned 502 at that still-required field, before any step or final envelope was observed. Private capture was again removed; no raw content or identity values were printed. This is evidence for a broader [optional lifecycle identity proposal](../roadmap.md#ownership-and-projection-decisions), not authorization to weaken it or proof that final identity/status, service reports or DONE are absent. The proposal separates HTTP-attempt stream ownership from optional reported metadata without relaxing status/outcome, call identity or EOF contracts.

The user then selected lifecycle-wide optional IDs with supplied-field validation and first-report binding. A subsequent one-request v1 text probe (2048 output tokens, 45 seconds, one attempt) reached final `completed` and client 200 through the current EOF/DONE gates. No lifecycle owner reported ID or service tier. This supports the selected sparse-ID profile for that run, not universal tier absence or tool-loop acceptance.

The separately bounded v1 SDK tool loop (at most eight serial requests, 2048 output tokens/45 seconds each, one candidate/attempt, no retries) stopped after its first Chat request; no corrective/final requests ran. A separate one-request structural diagnosis with temporary private capture found a `function_call` step containing nonempty string ID/name, object arguments and a string `signature`. The then-current thought-only profile rejected that owner before call closure. The probe observed no final envelope and cannot establish its status or service fields. Only shapes were reported; actual arguments, IDs and signatures were neither printed nor used as fixtures/replay input, and capture was removed.

The inspected [v1 function-call schema](https://ai.google.dev/api/interactions-api-v1) and [pinned SDK function-call type](https://github.com/googleapis/python-genai/blob/78f6d3412caaaed44f99ce57be2d16d0b8c407cb/google/genai/_gaos/types/interactions/functioncallstep.py) omit that signature field. The [stateless function-calling guide](https://ai.google.dev/gemini-api/docs/function-calling#stateless-function-calling) requires all model-generated steps, including thoughts and function calls, to be returned exactly as received; its REST examples use v1beta. The user separately selected the [observed-v1 call-only replay profile](../architecture.md#reasoning-replay). This is not silent field loss, thought reattribution or automatic admission from another protocol's signature rules, and it does not certify native input/SDK/installed-client behavior without their independent gates.

After that selected repair, a fresh CLI and native SDK accumulators passed a separately bounded v1 run: eight serial Generation requests, Chat four then Responses four, 2048 output-token cap/45 seconds/one candidate/one attempt each, SDK retries disabled. Both completed missing-file feedback → corrective call → final synthetic result → next-user full-history return. Independent synthetic native oracles additionally require distinct call/thought signatures on exact native owners, including input `function_call.signature`; real acceptance establishes the selected model/binding/SSE profile, not every stream shape, service report, installed client or replay across accounts. No actual signature, ID or business body was printed or retained as a fixture.

#### Streamed score scope, 2026-10-20

The user requested further streaming-scope research instead of selecting the proposed terminal-only aggregate profile. Public definitions and the supplemental Python SDK `364889a` establish the following boundaries:

| Evidence | Established meaning | Not established |
|---|---|---|
| [Developer API Candidate/LogprobsResult](https://ai.google.dev/api/generate-content#LogprobsResult) and pinned proto | Candidate average; sum for all tokens; token/top-candidate reports indexed by decoding step | Whether an SSE candidate's aggregates describe its content fragment, the cumulative candidate, or a later summary; no explicit merge/reset/coverage rule |
| [`models.py` streamed intake](https://github.com/googleapis/python-genai/blob/364889aafe40bfa8f3b9db847ba272d299f7d632/google/genai/models.py#L4775-L4814) | Parse and yield each native response separately | No shared probability accumulator or proof that last/sum is the correct reduction |
| [`StreamContinuation.observe`](https://github.com/googleapis/python-genai/blob/364889aafe40bfa8f3b9db847ba272d299f7d632/google/genai/_extra_utils.py#L880-L974) | Within-hop usage snapshots and across-hop usage have distinct rules; returned candidate scores are not accumulated there | Usage's documented accumulation rules do not transfer to scores |
| [`merge_pydantic_models`](https://github.com/googleapis/python-genai/blob/364889aafe40bfa8f3b9db847ba272d299f7d632/google/genai/_extra_utils.py#L1199-L1313) | Separate continuation-hop responses add numeric `_sum` fields and preserve the latest non-null scalar average | This helper is not an ordinary SSE-frame reducer or a guarantee of a combined candidate-wide average |
| [SDK probability types](https://github.com/googleapis/python-genai/blob/364889aafe40bfa8f3b9db847ba272d299f7d632/google/genai/types.py#L8192-L8235) | Token values and aggregate sum are optional; sum is marked unsupported in Vertex AI | SDK Optional/None does not establish every native JSON null/default rule or aggregate coverage |

A schema-expressible stream reporting sums `-0.2`, then `-0.6` has different reductions under disjoint fragments (`-0.8`) and cumulative snapshots (`-0.6`). The public field descriptions alone do not disambiguate them. A finish reason closes generation; it does not independently prove the score's token coverage. Missing final metrics cannot authorize carrying an earlier checkpoint forward as a reported final value. Explicit zero remains a value, not absence.

The continuation helper is also not an average oracle. In a hypothetical two-hop response with one token/sum `-1` and three tokens/sum `-6`, the combined mean would be `-1.75`; preserving hop two's mean yields `-2`. This is an arithmetic counterexample to treating the helper's latest scalar as a reweighted whole-output score, not an observed Provider defect or evidence that ordinary stream chunks are separate hops. The inspected SDK's `test_log_probs` uses non-streaming `generate_content`; continuation sum assertions are synthetic multi-request tests, not native streamed-score fixtures.

The [Vertex inference reference](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/model-reference/inference), rechecked on this date, warns that `responseLogprobs` and `logprobs` are deprecated for Gemini 3.x and will be deprecated completely. This is Vertex evidence, not a Developer API deprecation guarantee. The current [Gemini 3.8 Flash Developer model page](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-flash) does not settle the streamed-score contract.

No real Provider calls were made. A selected model/endpoint/API version and redacted native observations could establish a narrow profile, not a universal merge rule. Before selecting aggregate owners, require evidence for coverage, repeated reports, absence, terminal-only reports and content-free final frames. Keep general terminal explanations and source-bound token identity separate from this unresolved aggregation question. The [design proposal](../api-expansion-design.md#google-output-report-owners-unselected) remains unselected.

## Scoped accounting contract

The IR retains one latest typed `UsageReport` per operation or response-local step, including sparse modality, cache-TTL and tool-request detail owners. Updates replace their own scope; steps never sum into the operation. Final seals observation updates rather than claiming exhaustive billing. Content edits preserve the reports, and the usual operation usage view is derived rather than independently stored.

Let P = prompt input, U = tool-use prompt input, O = generated output excluding thoughts, R = thoughts, C = cached input:

- [generateContent UsageMetadata](https://ai.google.dev/api/generate-content#UsageMetadata) and pinned SDK `types.py` explicitly give `total = P + U + O + R`, with C within P. Store P/U/O/R separately, derive inclusive input P+U and output O+R, and never add C twice.
- Interactions `usage.py` describes `total_tokens` as prompt + responses + other internal tokens. The [function-calling reference example](https://ai.google.dev/api/interactions-api#CreateInteraction-function_calling) reports P=100, U=50, O=25, R=0, T=125, while supplementary reference fixtures use additive U. This does not establish one universal inclusion equation. Keep tool-input and total relationships unreported; do not choose a relation by arithmetic coincidence.
- The [streaming guide](https://ai.google.dev/gemini-api/docs/streaming) distinguishes cumulative `step.stop.usage` from local `step_usage`. Opening/status updates and terminal usage are operation snapshots. A terminal without another usage value seals the latest observed operation snapshot without adding step counts.
- Google modality lists belong separately to P, U, O and C. Interactions has corresponding `*_tokens_by_modality` fields. Missing categories do not establish zero or exhaustive coverage. Its `modalitytokens.py` permits missing/null category and count; retain unknowns. Google's omitted proto3 scalar zero retains explicit default provenance.
- Grounding tool counts are requests, not token consumption; missing counts remain unknown. Duplicate categories and sums exceeding their own known parent reject, but sparse lists need not equal their parent.

For P=100/U=30/O=20/R=7/C=40/T=157, generateContent yields a derived input of 130 and output of 27 while retaining every source bucket. The equivalent Interactions report preserves the numbers without claiming U's relation or rejecting T solely for not matching an assumed formula. O remains reported even when R is absent and an inclusive output cannot be derived.

The named `generation.usage-report-view.v1` delivery projection preserves the source report and records loss of unrepresented detail/scope/provenance on the target copy. OpenAI's scalar usage requires its known inclusion relation; an Interactions exchange may consequently deliver no scalar usage. Static and streamed omission agree, including reports containing only auxiliary detail. No downstream custom usage event is introduced.

Anthropic's [cache documentation](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) gives disjoint input/read/write categories and `cache_creation = five-minute + one-hour writes`; tool-request counts are separately priced observations. Native JSON and SSE now map these into operation reports. `output_tokens_details.thinking_tokens` remains an output subset, including internal delimiters; subtraction does not establish a visible-text token count.

The pinned `MessageDeltaUsage` has server-tool/thinking reports but no `cache_creation` TTL object. Full TTL and server-tool objects require both children. Optional null means no observation; non-null nested objects replace rather than field-merge or sum. Messages JSON and opening SSE preserve native TTL detail; late new/changed TTL detail rejects, while supported tool/thinking reports use delta fields. Missing generic children are not filled with zero. Exact details stay in the Messages delivery copy; OpenAI keeps its derivable scalar/reasoning view and records omitted breakdowns.

The pinned SDK fixture `tests/lib/streaming/fixtures/message_delta_fields_response.txt` changes the cache-write parent from 10 to 12 without another TTL report, while its reducer retains 10+0. That demonstrates SDK replacement behavior, not a valid exception to the documented arithmetic. The codec rejects the contradictory accumulated report instead of changing a source fact or weakening the global relationship. Input-transformation reports use the separate validated omission described above, not token accounting.

## Selected visible-history transfer

The user selected bounded visible-history transfer after reviewing [pi's actual transformer](https://github.com/earendil-works/pi/blob/8efd314fa3d3232ce197d8d7a6a5660530b9d83e/packages/ai/src/api/transform-messages.ts) and its [tool-turn test](https://github.com/earendil-works/pi/blob/8efd314fa3d3232ce197d8d7a6a5660530b9d83e/packages/ai/test/transform-messages-cross-model-thinking.test.ts). pi drops all foreign thinking rather than presenting it as assistant speech; it keeps ordinary content and call/results, and removes model-bound signatures. A local synthetic probe confirmed this behavior and source immutability without Provider calls.

MorphieCore follows that transfer direction, not pi's synthetic orphan results, image placeholders or generic removal of failed assistant output. Compatible replay retains dependency checks. Incompatible reasoning must have both a completed owner and final opaque value before omission; the transfer can happen before a final assistant answer. Required compacted/cached input remains protected. Unattributed readable reasoning is not assumed foreign. Native cross-format omission occurs before grouping so an omitted reasoning-only turn does not leave a fabricated empty message.

[Responses item-ID handling](https://github.com/earendil-works/pi/blob/8efd314fa3d3232ce197d8d7a6a5660530b9d83e/packages/ai/src/api/openai-responses-shared.ts#L313-L322) also matters: wire call-item IDs may be paired with removed reasoning. The target copy forgets those aliases in affected assistant runs without changing semantic call IDs or actual results. Damaged or missing compatible replay cannot be hidden by another owner's foreign omission.

This policy supersedes the earlier recommendation to reject all active-tool-turn transfer by default. Native API replay requirements do not themselves forbid a different model receiving a visible transcript; transfer is an explicit loss of internal state, not equivalent continuation. Foreign part/call values are cleared without deleting their visible owners.

## Messages budget and identity boundaries, 2026-10-19

The [extended-thinking guide](https://platform.claude.com/docs/en/build-with-claude/extended-thinking), [Messages reference](https://platform.claude.com/docs/en/api/messages) and [Haiku 5.5 reference](https://platform.claude.com/docs/en/models/haiku-5-5/overview) were rechecked on 2026-10-19. Source/code findings and the subsequent user-selected scope are distinguished below; neither is Provider acceptance.

- **Numeric thinking:** manual `thinking: {type: "enabled", budget_tokens: N}` is distinct from adaptive thinking plus effort. Ordinary manual budgets are at least 1024 and less than `max_tokens`; the guide separately permits larger budgets for supported manual interleaved thinking because their scope spans thinking blocks in the assistant turn. Haiku 5.5 documents adaptive thinking, not a manual-budget carrier.
- **Current gap:** Messages client intake retains a numeric budget, but the native profile encodes only disabled/adaptive thinking. Trusted `budget_to_effort` is an explicit lossy alternative, not exact carriage. The current IR globally rejects budget greater than output ceiling and allows equality; it cannot represent the documented interleaved exception or independently enforce the ordinary Messages strict inequality.
- **Selected budget scope:** support ordinary manual budgets only for now, enforcing the source/target minimum and strict inequality. Defer and reject requests requiring the wider manual-interleaved scope; no new scope abstraction is selected for this slice. Keep P3b and no-clipping rules. Adding the codec carrier does not enable manual thinking on Haiku or change adaptive tool loops; do not claim complete manual-mode coverage.
- **User attribution:** `metadata.user_id` is an optional nullable opaque end-user identifier for abuse attribution, not an authentication or conversation identifier. The current reference permits up to 512 characters and forbids personal identifying information. The [pinned SDK type](https://github.com/anthropics/anthropic-sdk-python/blob/bcd55fe1d3f0f1240765f8cef04295b67337f55a/src/anthropic/types/metadata_param.py) confirms its optional/null shape and purpose.
- **Current gap:** client intake ignores the whole `metadata` container; native Messages has no metadata carrier. `ExecutionHints.identity.user` currently bounds values to 256 characters. Exact carriage needs source validation, sufficient bounded storage and target-local limits.
- **Selected attribution policy:** the subsequent [three-Provider comparison](#cross-provider-user-attribution-2026-10-19) supersedes the earlier prohibition on mapping user attribution into safety identifiers. Preserve independent source fields; project shared attribution to admitted safety carriers under explicit priority and conflict rules. Authentication, routing, credentials and session identity remain separate. The Messages carrier and shared-bound change remain implementation work.

Model-effective validation is separate from protocol grammar. The [Gemini 3.8 Flash page](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-flash), rechecked on the same date, lists low/medium/high thinking, rejects minimal and limits output to 65,536 tokens. The generic encoder still carries minimal and 65,537, as the earlier P7 probes showed. The selected design keeps limits in a small trusted binding policy, checked after projection by the shared preflight/preparation encoder, including ordered effort updates and inserted defaults. Preserve protocol-wide carriers and existing selected mappings. Do not add clamping now; a concrete compatibility problem may motivate a separate field-specific decision later. This is selected ownership and policy, not implemented model guards.

### Attribution carrier recheck, 2026-10-20

The [Responses reference](https://developers.openai.com/api/reference/resources/responses/methods/create) was rechecked: safety identity is an optional nullable string of at most 128 characters. Bigtable's additional resource-specific byte bound is not inferred for generateContent; its schema supplies the selected codepoint bound. This is source-backed grammar interpretation, not a live Google enforcement result.

Current shared storage bounds are 512 general-user and 128 safety characters, with independent native OpenAI 256/128 checks. [Target projection](../../src/protocol/attribution.rs) implements the selected field priority and value-free identity/legacy-cache loss evidence; Google emits only the fixed safety label and Interactions emits no inferred carrier.
